# Live logs and status for every CLI and agent (20261111)

Order: ThreadDesk board `188ce4729a62`, ordinal 660, entry `2942c5883ae4`
(`live-logs-implementation-freedom-20261111`). Priority 1 of the Big Plan.

## Purpose

KiraBridge needs direct access to the running logs and status of every CLI and
agent it runs, including adapters added later. User-visible presentation is not
required. The implementation therefore exposes one bounded, machine-readable
source per execution task and lets agents read it through the existing MCP
surface.

## Where the data comes from

Recording happens in two existing funnels, so a newly configured CLI or agent
adapter is covered without per-adapter logging code:

- `TerminalManager` drains the managed child's `stdout`/`stderr`. Every current
  process-based adapter (Codex, Claude Code, Gemini CLI, Copilot CLI, OpenCode,
  Grok ACP, visible handoffs, plain `terminal.execute`) and any future adapter
  that reuses `TerminalManager` is captured. Chunks are decoded with an
  incremental UTF-8 decoder, so split multibyte characters stay intact.
- `Bridge.execute` forwards every `running`/`progress` adapter event as an
  `events` line. HTTP/ACP transports (Grok API, OpenCode HTTP) and future
  transports that only report progress are covered by the same rule.

A future transport with neither a managed child process nor progress events
calls `bridge.live_logs.append(task_id, principal, channel, text)` directly; the
source is created on first use and needs no registration.

One source id is the task id. The source metadata carries the operation, agent
name, transport, working directory, child PID, state and exit code.

## Access

- MCP tool `live_logs` (read-only annotation) and operation `logs.live`
  (capability `logs.live`, effect `read`).
- Omit `source_id` to list every source owned by the caller.
- Pass `source_id` and the previous `next_cursor` to read only newer lines;
  `reset=true` means the ring buffer dropped older lines, `dropped` counts them.
- `channels` filters `stdout`, `stderr` and `events`.
- `agent_status` now includes a text-free `live_logs` summary for the same
  principal.

## Bounds and safety

- In-memory only, per source: 400 lines / 128 KiB / 4096 characters per line
  (`live_logs` config section, `enabled` switch).
- At most 64 sources; the oldest closed source is evicted first. A live source
  is never displaced: if every slot is live, the new source is refused and the
  `dropped_sources` counter is increased.
- Sources are strictly principal-scoped. Another principal's source is neither
  listed nor readable; a colliding task id from another principal cannot
  overwrite it.
- Recording is observation only. It never attaches to a foreign process, reads
  unrelated files, retries work, types input, terminates anything or changes a
  task's state. A recording failure is swallowed and cannot fail the observed
  task.
- This hub is not a second audit source. Durable evidence stays in task
  records, the audit trail and the hash-referenced output stores.

## Verification

`tests/test_live_logs.py` covers cursor semantics, drop/reset reporting,
principal isolation, source bounds, the disabled switch, a real child process
end-to-end (stdout, stderr, spawned event, closed state, exit code), the
`logs.live` read operation, capability gating, the `agent_status` summary and
MCP tool registration.
