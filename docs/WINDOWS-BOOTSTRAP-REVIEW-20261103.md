# Independent Windows bootstrap review · 3 November 2026

Reviewed source `d8404f7`: `windows_dev_vm.py`, `windows_guest_host.py` and
`windows_guest_runner.ps1`. No VM was launched; no existing VM, disk or productive
KiraBridge service was changed.

Two concrete receipt defects were corrected before guest execution:

1. Existing successful phase reports could be reused after a manifest change.
   Both attempt and final report must now match the current manifest SHA256 and
   phase before publication/reuse. A stale, missing, failed or uncertain record
   never grants another native attempt.
2. Attempt receipts were closed without an explicit durable flush. The file
   stream now calls `Flush(true)` before returning to launch. Reports use the
   same exclusively created, flushed receipt writer and cannot overwrite prior
   evidence.

The real PowerShell functions were executed locally using PowerShell **7.4.0**:
seven scenarios cover fresh success, same-payload readback, changed payload,
independently stale attempt/report, failed/missing/uncertain evidence and exclusive
file preservation. One pytest wrapper passed. Native commands were replaced with
an explicit test stub; this is executable bootstrap control-flow evidence, not
Windows PowerShell 5.1 or keyboard acceptance. The guest still supplies that check.

The actual installed UTM **5.0.8 qemu-img** library checked a new, own temporary
80-GiB QCOW2 generated by `empty_qcow2`: **exit 0, check-errors 0**, physical end
262144 bytes and 1310720 virtual clusters. No VM ran. The library was invoked in
a short-lived child with only that child's framework search path set to the
installed app's frameworks. Initial harness attempts hit library-loading/old
Python compatibility issues, not an image error; the final native checker output
is the recorded result. The temporary image was removed normally.

QEMU, Network and Drive plist keys were checked against the
[UTM v5.0.8 QEMU source](https://github.com/utmapp/UTM/blob/v5.0.8/Configuration/UTMQemuConfigurationQEMU.swift),
[Network source](https://github.com/utmapp/UTM/blob/v5.0.8/Configuration/UTMQemuConfigurationNetwork.swift)
and [Drive source](https://github.com/utmapp/UTM/blob/v5.0.8/Configuration/UTMQemuConfigurationDrive.swift).
The e1000 NIC follows the q35 default. The
[QEMU user-network contract](https://www.qemu.org/docs/master/system/devices/net.html)
is consistent with the chosen 10.0.2.2 host endpoint. Actual guest connectivity
remains a boot-time test. English `Administrators` is correct even with a German
image: [Windows Shell Setup localizes these group names](https://learn.microsoft.com/en-us/windows-hardware/customize/desktop/unattend/microsoft-windows-shell-setup-useraccounts-localaccounts-localaccount-group).

The generated configuration names exactly one new writable disk; installer
partitioning targets disk0/partition3. Read-only install/seed media, no host
folder/clipboard/USB sharing, token-bound loopback file serving, SHA256-pinned

not certify a successful Windows install, the host's Windows11 support status,
first-logon networking or native guest execution.
